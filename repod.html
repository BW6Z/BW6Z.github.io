Why I built it

A development request mixes difficult engineering with routine edits. Sending everything to one strong model can waste money; moving simpler tasks to another tool means repeating context and coordinating the work yourself.

Repod makes that coordination explicit. A Meta model splits a request into tasks, labels their complexity and impact, and chooses an executor for each. The user approves the plan, while the program enforces a minimum model capability for risky work.

What I built

  1. Plan with the user. Clarifying questions, a proposed task plan, and approval happen in one conversation.
  2. Route by complexity and impact. Complex or high-impact tasks must use a strong model. Simpler work can use a lower-cost model.
  3. Check and repair. Type checks and tests run after each task. On failure, Meta decides whether to repair on the same model, escalate, or stop; program limits constrain that decision.
  4. Freeze and evaluate. For the fixed demo request, hidden holdout tests run once on the frozen result. Their failure details are not returned to the models for repair.
  5. Make the work inspectable. The viewer shows the conversation, attempts, decisions, delivered diff, token usage, and cost by phase. The static replay needs no API key.

Stack: TypeScript, Node.js 24, Zod, the Responses API, and a plain HTML/CSS/JavaScript viewer. Engineering work also includes isolated working copies, file write scopes, budget reservations, event logging, and CI checks on Windows and Ubuntu.

Meta models and where they ran

All recorded real runs used Meta open-weight models served through OpenRouter.

Muse Spark Open

Coordinates planning and routing, handles complex work and review, and decides how to respond to failed checks.

Muse Glimmer 30B

Handles routine work and documentation in the cost-oriented preset. Failed work can be repaired on Glimmer before escalation.

The repository also includes a Meta Model API configuration, but that endpoint was not used for the recorded real runs.

The recorded demo

The fixed request adds dependency-order planning to a small TypeScript library: a planning algorithm, a CLI command, and documentation with a runnable example.

Meta assigned the planner and CLI to Spark Open, and the docs task to Glimmer. The first two tasks passed immediately. The docs example failed a type check once; Meta chose to repair it on Glimmer, and the next attempt passed.

The run completed, and the frozen result passed all 31 hidden tests. It delivered ten changed files, including three visible test files supplied by Repod. Total cost was $0.0902, with about $0.0100 spent on coordination.

Engineering lessons and next steps

  • Review needs evidence. Early reviewers raised concerns about code that had passed checks. Providing the check results and interface contract helped ground their judgments.
  • Output limits affect comparisons. The shared 16,000-token executor cap stopped one single-model run. Per-model output limits are a follow-up.
  • Verification has a scope. The hidden tests validate the fixed demo request. Free-form requests currently run only on the bundled sample library, checked by its type check and existing tests.
  • Isolation needs more work. Separate working copies and restricted child-process environments are implemented; operating-system sandboxing, support for other repositories, and generated checks remain planned.
